# 2c · Activity (what the agent did and why) and "Your usual order"

Status: open · Wave 2: start after 1b, 1c and 2b are merged · Shared contract: [`README.md`](README.md).

## Why

From the UI review (14 Nov): the buyer must be able to see, for every order, what the agent did and why it decided that way. Trust needs a readable trail, not only hashes. The mockup has a third tab **Activity** with a list of orders and, per order, a timeline from "you asked" to "Valio Aimo confirmed", with one plain sentence per line: "Your usual. Passed 3 musts. Finnish ✓. Ordered alone under g1 (≤ €600)."

The start screen also gets a **"Your usual order"** card: the usual products with their usual amounts, an estimated total, and "Order the usual" (one click into the normal read-back).

Mockup moments: Activity tab (list with badges, order detail timeline), start screen "Your usual order" card and the short "Recent orders" list.

## What exists (after wave 1)

* 2b: `GET /orders` (list with tier, total, labels), `GET /autonomy`.
* 1c: `offers` events with `funnel`, `usual` flags; the `usual` diff check.
* 1b: kitchen profile with `usual[]` (`word`, `product_id`, `product_name`, `typical_qty`, `unit`, `per`).
* mcp-server: `GET /internal/orders/{id}` (order data: intent, lines, diff checks per line, tier, `grants_used`, approval, receipt), `GET /internal/orders/{id}/audit` (every tool call with summary and data: searches with `excluded_count`, `check_offer` with recommended product, decisions), `GET /verify/{id}`.

## Build

### 1. `GET /orders/{order_id}/story` (backend, `routes_orders.py`)

Builds one readable timeline from the order, its intent and its audit trail. No new data at Valio Aimo; if a field is missing, it is left out, never invented.

```json
{
  "order_id": "ord_41", "label": "You decided 1", "tier": "ask", "total": 512.0,
  "mandate": {"version": 3, "grants_used": ["g1"]}, "kitchen_profile_version": 7,
  "steps": [
    {"kind": "asked", "at": "...", "text": "for next week", "attachments": ["up_…"]},
    {"kind": "understood", "at": "...", "intent_id": "int_…", "intent_hash": "…", "signed_by": "Anna Virtanen", "items": 5},
    {"kind": "searched", "at": "...", "items": [{"item_id": "i1", "word": "milk", "funnel": [...], "picked": "Valio Eila® …", "why": "Your usual. Passed 3 musts. Finnish ✓. Cheapest of 1 option."}]},
    {"kind": "decided", "at": "...", "lines": [
       {"item_id": "i1", "outcome": "alone", "grant": "g1", "why": "No deviation, inside €600 (g1)"},
       {"item_id": "i5", "outcome": "blocked", "rule": "m1", "evidence": "Supplier label 9 Nov: MAY_CONTAIN tree nuts (GS1)"},
       {"item_id": "i5", "outcome": "you", "by": "Anna Virtanen", "why": "Replaced by Nut-free oat muesli (+€4.80)"}]},
    {"kind": "confirmed", "at": "...", "receipt": {...}, "verify_url": "/orders/ord_41/verify"},
    {"kind": "learned", "at": "...", "text": "\"granola\" now means Nut-free oat muesli (kitchen profile v8)"}
  ]
}
```

* `why` sentences are generated by code from the data (rule labels, preference results, grant limits), not by an LLM, so they are always true. Template per outcome; keep them under 15 words.
* `learned`: from the kitchen profile's `sources` with `order_id` (2a writes them; if 2a is not merged, skip).
* Add to `contracts/backend-api.yaml` with a fixture built from a real demo run (`contracts/fixtures/order-story.json`).

### 2. `GET /kitchen/usual-order` (backend, `routes_kitchen.py`, owned by 1b; add only this route)

```json
{"items": [{"word": "milk", "product_id": "463038", "product_name": "Valio Eila® …", "quantity": 120, "unit": "L",
            "last_unit_price": 1.09, "estimate": 130.80}],
 "estimate_total": 541.95, "deliver_by": "2026-11-16", "based_on": "your usual amounts per week"}
```

* Items: active usual products with `typical_qty`. Last unit price from the most recent order line with that product (via `GET /orders` data); missing → `estimate: null`.
* "Order the usual" in the UI sends `POST /chat {"message": "Order the usual", …}`. 1c's prompt rule already turns "the usual" into all usual items; check that it uses the same amounts as this endpoint (both read the kitchen profile).

### 3. Activity list

The list itself is 2b's `GET /orders`. Add `kitchen_profile_version` to each order if the backend knows it (store it in the session when the intent is proposed).

## Not in this package

* Price estimates in the read-back (package 3.4).
